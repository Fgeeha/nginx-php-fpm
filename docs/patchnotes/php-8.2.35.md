# PHP 8.2.35 / Alpine 3.24 — 22 октября 2026

Базовый образ обновлён с `php:8.2.7-fpm-alpine3.18` до
`php:8.2.35-fpm-alpine3.24`. PHP 8.2.35 исправляет CVE-2026-109618 и
CVE-2026-109619, затрагивающие в том числе PHP-FPM:
[рекомендация PHP](https://www.php.net/archive/2026.php).

## Совместимость образа

Контрольный образ — опубликованный `richarvey/nginx-php-fpm:3.1.6`
с PHP 8.2.7. Его manifest:
`sha256:fdaa086c82611024776048db9d1eec6324aa1058e1d867a15004c92d24df6187`.

| Компонент | Прежний образ | Новый образ |
|---|---|---|
| PHP | 8.2.7 | 8.2.35 |
| Alpine | 3.18 | 3.24 |
| Redis PHP | 5.3.7 | 5.3.7 |
| Xdebug | 3.2.1 | 3.2.1 |
| MongoDB PHP | 1.15.3 | 1.21.12 |

Версии PECL закреплены: обновление PHP больше не переводит Redis и MongoDB
на очередную основную версию незаметно для приложения. MongoDB 1.15.3
не собирается с новым musl; выбрана актуальная версия ветки 1.x
[из списка релизов](https://pecl.php.net/package/mongodb).
Это обновление MongoDB требует отдельной проверки приложений, которые
используют драйвер, их Composer-ограничений и версии сервера MongoDB.
Сохранение ветки 1.x само по себе не гарантирует совместимость всех БД.
Начиная с [драйвера 1.20](https://github.com/mongodb/mongo-php-driver/releases/tag/1.20.0)
не поддерживается MongoDB Server 3.6; требуется Server 4.0 или новее.
Начиная с [драйвера 1.16](https://github.com/mongodb/mongo-php-driver/releases/tag/1.16.0)
Queryable Encryption требует нового протокола и Server 7.0 или новее.

Ни один ключ окружения контрольного образа не удалён. Значения `LD_PRELOAD`,
`LUAJIT_INC`, `LUAJIT_LIB`, `PATH`, `PHP_INI_DIR`, `fpm_conf`, `php_conf` и
`php_vars` совпадают. `GPG_KEYS`, `PHP_URL`, `PHP_ASC_URL`, `PHP_SHA256`,
`PHP_VERSION`, `PHPIZE_DEPS` и флаги компиляции наследуются от новой PHP-базы.
Старые значения метаданных PHP 8.2.7 не нужно переносить в окружение контейнера.
Сохранены порты 80/443, `/start.sh`, рабочий каталог `/var/www/html`,
Nginx, Supervisor, Lua/NDK, Composer, Certbot и команды pip.
После восстановления FTP совпадает полный набор из 48 расширений PHP.
`ENTRYPOINT`, `CMD`, рабочий каталог и объявленные порты совпадают
с контрольным образом. На AMD64 и ARM64 проверены обычный запуск контейнера и
полный `docker restart`, без подмены `ENTRYPOINT`.

## Исправленные несовместимости

- Настройка сокета FPM теперь учитывает закомментированный `listen` в новом
  шаблоне; проверяется тот же конфиг, который запускает Supervisor.
- Вместо `chown nginx.nginx` используется `chown nginx:nginx`.
- Возвращено расширение FTP с TLS, отсутствующее в новой PHP-базе.
- Certbot устанавливается пакетом Alpine, без изменения системного Python
  через pip. Сам pip сохранён для существующих сценариев.
- Устранена двойная загрузка OPcache, сохранён параметр `OPcache=1` для
  отключения. Отсутствие дополнительного OPcache ini не ломает сборку.
- Старые Redis/Xdebug собираются в режиме C17, необходимом с GCC 15.
- `ENABLE_XDEBUG=1` задаёт режим debug без повторной загрузки расширения.
  Наличие расширения по умолчанию сохранено, как в контрольном образе.
- Удалена установка `hirak/prestissimo`, несовместимого с Composer 2.
  Production устанавливает зависимости с `--no-dev`, development — с dev.
  **Несовместимое изменение:** при ошибке `composer install` запуск теперь
  завершается с ошибкой;
  `SKIP_COMPOSER=1` сохраняет прежнее назначение.
- Скрытие версии PHP изменяет `php.ini`, а не конфигурацию FPM.
  `HIDE_NGINX_HEADERS=0` по-прежнему разрешает версии в HTTP-заголовках.

## Проверки

AMD64: образ собран, оба smoke-теста OPcache прошли. Все 16 сценариев
совместимости прошли:

- версии расширений; Unicode iconv, GD/JPEG, SQLite и BSON roundtrip;
- PHP memory/post/upload limits, ошибки, окружение, WEBROOT, catchall и real IP;
- Xdebug, UID/GID и запись файла PHP-воркером;
- Git branch/tag/commit и повторный старт с сохранением файлов;
- Composer production/development/skip и отказ при несовместимом lock;
- HTTP-заголовки, пользовательский Nginx-конфиг и startup-скрипты;
- HTTPS с проверкой локального сертификата, загрузка Lua/NDK и Lua через HTTP.

ARM64: `make check PLATFORM=linux/arm64 IMAGE=nginx-php-fpm:arm64`
завершился успешно под QEMU на AMD64-хосте. Собран образ архитектуры `arm64`;
оба smoke-теста и все 16 сценариев совместимости прошли, включая HTTPS,
FTP/TLS API и Lua/NDK. Обычный запуск и полный `docker restart` прошли.

### Исходники рабочего портала

Проверялось текущее рабочее дерево портала, включая
незакоммиченные изменения, а не только Git-ревизия `2326fea`.
Контрольная сумма набора PHP-файлов, выводимая тестом:
`f8da04a159154b3e47b5ceeb016f0039b45b3b1ee8bc91344722065229bb1b8a`.

На PHP 8.2.7 AMD64, PHP 8.2.35 AMD64 и PHP 8.2.35 ARM64 прошли
синтаксические проверки всех 54 PHP-файлов и обращения к главной странице,
news, partners, FAQ, documents,
how-to-join, policy, support, cert-programs и CSS. Хеши всех 10 ответов
совпали побайтово между всеми тремя запусками. ARM64-процесс подтвердил
`aarch64`. POST через `siteapi/news-list.php` вернул ожидаемый JSON.
Исходники подключались только для чтения; `.env` исключён, CMS/API заменены
локальными заглушками с пустыми коллекциями, внешняя сеть отключена.
Код портала не изменялся.

Это проверка исходников production-приложения в изолированном окружении.
Рабочий сервер, его собственные Nginx rewrite-правила, реальные CMS/API,
авторизация и бизнес-данные не проверялись: конфигурация и доступ к ним
не предоставлены. Реальные подключения MongoDB/Redis и выпуск/продление
ACME-сертификатов также не проверялись. Эти результаты не означают, что
любой PHP-проект можно обновить без проверки его зависимостей.

## Повторение проверок и обновление

```sh
make check IMAGE=nginx-php-fpm:local
make check PLATFORM=linux/arm64 IMAGE=nginx-php-fpm:arm64
make test-portal IMAGE=nginx-php-fpm:local APP_DIR=/path/to/php-project
make test-portal IMAGE=nginx-php-fpm:arm64 APP_DIR=/path/to/php-project
```

На AMD64 для запуска ARM64 нужен QEMU/binfmt. Эмуляция проверяет код ARM64,
но не заменяет замеры производительности на реальном ARM-сервере.
Сборка не является побитово воспроизводимой: пакеты Alpine и Composer
загружаются из обновляемых источников.

Собранные образы локальные; публикация в registry и обновление рабочего
сервера не выполнялись. Для обновления нужно опубликовать новый тег в своём
registry, заменить только ссылку на образ в рабочем развёртывании, сохранить
прежние volumes/env/порты/Nginx-конфиги и пересоздать контейнеры. Обычный
`docker restart` продолжит использовать старый образ. Перед обновлением
следует сохранить прежний тег/дижест и резервную копию изменяемых данных;
откат выполняется пересозданием контейнера из прежнего образа.
